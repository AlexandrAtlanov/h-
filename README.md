# Юридический ассистент банка (RAG)

Ассистент отвечает сотрудникам банка на юридические вопросы по базе из 21 документа: 8 документов компании (договоры аренды и поставки, допсоглашение, регламенты двух редакций, служебные записки) и 13 законов (ТК, НК, КоАП, 152-ФЗ, МРОТ). Каждый ответ опирается только на найденные положения базы и содержит ссылку на документ и пункт. Если подтверждения в базе нет, ассистент прямо пишет, чего не хватает, и не отвечает по памяти.

Проект сделан на хакатоне Hack & Change 2026, кейс ПСБ «Юридический ассистент», командой из 4 человек.

**Итог: 50 место из 151 команды, скор 35.889, прогон 233 с при лимите 20 минут.** Точная версия лучшего сабмита: ветка `best-submission`, тег `sub-16-2`.

## Результаты и выводы

Оценка платформы: LLM-судья сравнивает ответ команды с эталоном и ответом baseline, два раунда со сменой порядка, Score = 0.7 x Match + 0.3 x Win. Выдуманный факт обнуляет вопрос. Лимиты прогона: 20 минут, 8 CPU, 16 ГБ, ZIP до 128 МБ, библиотеки только из разрешенного списка, 5 сабмитов в день.

История сабмитов онлайн-этапа:

| Сабмит | Что изменилось | Скор | Время прогона |
|---|---|---|---|
| agent | агент v1: гибридный поиск BM25 + bge-m3, метаданные чанков, самопроверка фактов | 31.306 | 526.3 с |
| simple | тот же поиск без агента, один проход LLM (контроль нижней границы) | 25.865 | 169.8 с |
| role2_agent | переписанные промпты планировщика и ответа | 30.917 | 202.2 с |
| B_more_context | больше контекста: TOP_K 8, 26 чанков в промпте, 8 соседей | 31.083 | 137.1 с |
| sub-16-2 | реранкер Qwen3 Reranker 8B + второй круг допоиска | 35.889 | 233.1 с |

Выводы:

- агентная схема против одного прохода LLM: +5.4 балла;
- реранкер и второй допоиск: +4.8 балла, самый крупный единичный рычаг. До последнего сабмита реранкер фактически не работал: переменную `RERANKER_MODEL` платформа не передает, а дефолта в коде не было. Урок: проверять фактическое окружение платформы, а не предполагаемое;
- больше контекста не меняет балл, но ускоряет прогон в 3.8 раза: критик чаще отвечает сразу, без допоиска;
- запас по времени в финале 5x (233 с из 1200), страховка на случай приватного сета большего размера.

## Быстрый запуск (Docker)

Нужны Docker и Docker Compose. Порт по умолчанию 8000 (меняется переменной `APP_PORT` в `.env`).

```bash
cp .env.example .env      # Windows: copy .env.example .env
# впишите в .env адрес API и ключ (см. «Настройка»)
docker compose up --build
```

После запуска откройте <http://localhost:8000>. При первом запуске строится индекс документов (до минуты), статус виден в интерфейсе.

Остановка: `docker compose down`. Индекс сохраняется в volume `index-cache`. При изменении базы знаний удалите volume и постройте индекс заново: `docker compose down -v && docker compose up --build`.

## Проверка без ключей API

Заглушка из `eval/` возвращает фиксированные ответы, этого достаточно для проверки интерфейса:


## Настройка

Используется любой OpenAI-совместимый API. На платформе хакатона адрес и ключ передаются организаторами через переменные окружения; для локального запуска впишите их в `.env` (файл не попадает в git).

| Переменная | Назначение | Пример |
|---|---|---|
| `LLM_BASE_URL` | адрес API (`/chat/completions`, `/embeddings`, `/rerank`) | `https://your-proxy.example/v1` |
| `LLM_API_KEY` | ключ API | нет |
| `LLM_MODEL` | модель ответа | `deepseek/deepseek-v4.1-flash` |
| `EMB_MODEL` | модель эмбеддингов | `baai/bge-m3` |
| `EMB_BASE_URL`, `EMB_API_KEY` | отдельный адрес и ключ для эмбеддингов (по умолчанию как у LLM) | нет |
| `RERANKER_MODEL` | реранкер, необязателен, пусто значит выключен | `qwen/qwen3-reranker-8b` |
| `RERANKER_BASE_URL`, `RERANKER_API_KEY`, `RERANKER_TOP_N` | настройки реранкера | `8` |
| `TOP_K`, `MAX_WORKERS`, `TEMPERATURE` | фрагментов на запрос, параллельность, температура | `8`, `6`, `0` |
| `APP_PORT` | порт веб-чата | `8000` |

Официальный `api.deepseek.com` поддерживает чат, но не `/embeddings`: без endpoint для `bge-m3` поиск автоматически работает только по BM25.

## Архитектура

```text
браузер -> FastAPI (app/) -> LegalService +-> LegalAgent (agent.py, prompts.py)
                                  |        1. планировщик запроса     (1 вызов LLM)
                                  |        2. гибридный поиск rag.py  (BM25 + bge-m3 + реранкер)
                                  |           + шапки, допсоглашения, другие редакции
                                  |        3. ответ или допоиск       (1 вызов LLM, до 2 допоисков)
                                  |        4. самопроверка фактов     (без LLM, +1 вызов исправления)
                                  +-> API документов и фрагментов
платформа -> solution.py -> тот же LegalAgent -> submission.csv
```

**Поиск (`rag.py`).** Документы делятся на фрагменты по разделам и пунктам договоров и по частям статей законов. У каждого фрагмента есть карточка метаданных: вид и номер документа, контрагент, дата, редакция, статус «утратил силу», связь с допсоглашением, номера пунктов. Поиск гибридный: BM25 (точные номера, суммы, названия) и векторы bge-m3 (смысл), объединенные через Reciprocal Rank Fusion. Фрагменты договора, номер или контрагент которого назван в вопросе, поднимаются выше; «Альфа-Трейд» не совпадает с «Альфа-Трейдинг». Реранкер Qwen3 включен по умолчанию, при сбое endpoint поиск продолжает работать без него. Если недоступен эмбеддер, поиск продолжает работать на BM25.

**Ответ (`agent.py`, `prompts.py`).** Планировщик переформулирует вопрос с учетом истории диалога и разбивает его на темы. К найденным фрагментам добавляются шапки документов, допсоглашения к договорам и тот же пункт другой редакции, чтобы модель могла выбрать редакцию, действовавшую на дату события. Модель отвечает только по фрагментам в формате: прямой ответ, затем документ и пункт, всего 2-4 предложения, и возвращает статус и использованные фрагменты.

**Проверка достоверности.** Каждое число, номер пункта, статьи и документа в ответе ищется во фрагментах, которые видела модель (функция `find_unsupported` в `agent.py`). При расхождении выполняется один вызов исправления; если неподтвержденные сведения остались, предложения с ними удаляются.

**Решение об отказе и уточнении** (правила в `prompts.py`):

| Ситуация | Поведение | Статус |
|---|---|---|
| ответ есть во фрагментах | ответ со ссылкой, отказ запрещен | `ANSWERED` |
| ложная предпосылка в вопросе | прямое исправление по документу | `ANSWERED` |
| подтверждена только часть | ответ на подтвержденное + чего не хватает | `PARTIAL` |
| темы нет в базе | обоснованный отказ без ответа по памяти | `REFUSED` |
| неясно, о каком договоре или контрагенте речь | уточняющий вопрос с вариантами | `CLARIFY` |
| противоправная просьба | отказ с разъяснением требований | `REFUSED` |
| непрофильный запрос | объяснение границ компетенции | `OFF_TOPIC` |

Инструкции внутри документов и реплик («игнорируй остальные документы», «ты теперь...») считаются данными и не выполняются; поддельные системные сообщения из истории диалога отбрасываются.

## Оценка качества

Папка `eval/` имитирует платформу: прогоняет решение на наборе вопросов с эталонами, оценивает ответы LLM-судьей по методике лидерборда и отдельно считает выдумки и ложные отказы.

- раннер собирает окружение платформы (`DATA_DIR`, `LLM_*`, лимит времени) и запускает `solution.py` как есть;
- судья: два раунда со сменой порядка A/B, выдумка по вердикту обнуляет вопрос, verdict-кэш на повторы;
- детектор выдумок без LLM: числа, пункты, статьи и номера документов проверяются против текстов базы;
- метрика ложных отказов: эталон отвечает, а решение отказалось;
- карта базы `kb_map.json`/`kb_map.md`: 21 документ, ключевые пункты, связи допсоглашений и редакций, ловушки и темы вне базы;
- приемочный тест конвейера на детерминированном мок-LLM, без ключей.

```bash
python -m eval.selfcheck                                  # регресс-проверки детекторов, без ключей
bash eval/smoke.sh                                        # полный конвейер на мок-LLM
set -a; source .env; set +a
python -m eval.run_eval --repo . --set demo --tag my-run   # реальный прогон, нужен .env
```

Отчет: `eval/reports/<tag>/report.md`. Ограничение: промпт платформенного судьи неизвестен, локальный судья его приближает, поэтому локальные баллы не сравниваются с платформенными напрямую.

## Сборка сабмита

```bash
python build_index.py        # необязательно: заранее посчитать индекс в kb_index_data.py (нужен ключ)
python make_zip.py           # архив в dist/: solution.py, agent.py, prompts.py, rag.py, requirements.txt
```

`solution.py` читает `DATA_DIR/questions.csv` и архив базы, обрабатывает вопросы параллельно и пишет `submission.csv`. Укладывается в лимит 20 минут: после 14-й минуты новые вопросы идут упрощенным путем (один вызов LLM), к 18-й минуте файл записывается в любом случае. `make_zip.py` проверяет, что в архиве нет ключей и библиотек вне разрешенного списка.

## Структура репозитория

```text
solution.py            точка входа платформы: questions.csv -> submission.csv
make_zip.py            сборка и проверки архива сабмита
build_index.py         предрасчет индекса в kb_index_data.py
agent.py               агент: планировщик, критик, допоиск, самопроверка
prompts.py             промпты планировщика, ответа и исправления
rag.py                 чанкинг с метаданными, гибридный поиск, реранк
app/                   веб-чат: FastAPI, панель источников, каталог документов
eval/                  локальная оценка: раннер, судья, детекторы, смоук
data/                  база знаний и вопросы (материалы кейса организаторов)
```

## Команда и процесс

Команда из 4 человек, зоны ответственности:

| Зона | Файлы |
|---|---|
| поиск и сабмит | rag.py, solution.py, build_index.py, make_zip.py |
| агент и промпты | agent.py, prompts.py |
| оценка и база знаний | eval/, kb_map.json, kb_map.md |
| веб-чат, Docker, материалы | app/, Dockerfile, compose.yaml |

Процесс: короткие ветки по зонам, PR в main только после прогона локальной оценки, журнал сабмитов в SUBMISSIONS.md, план и статус в PLAN.md и STATUS.md.

## Ограничения

- ассистент не использует внешние источники и собственные знания модели для юридических выводов;
- законы в базе только в действующей редакции: если нужна старая редакция закона, ассистент сообщает, что ее нет;
- самопроверка фактов эвристическая: проверяет числа, пункты, статьи и номера документов, но не числительные прописью и не смысл утверждений;
- при отсутствии подтверждения в базе ответ не подменяется догадкой;
- без доступного endpoint эмбеддингов поиск работает в режиме BM25;
- ключи хранятся только в `.env` или секретах окружения;
- в базе тестовые документы вымышленной компании ООО «Меридиан», реальных документов банка нет.
